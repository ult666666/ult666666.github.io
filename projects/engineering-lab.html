RelayBox

A signed webhook inbox with a durable SQLite job lifecycle. Delivery IDs deduplicate matching payloads, conflicting reuses are rejected, and expiring leases let a new worker recover interrupted work.

A fencing token prevents an old worker from acknowledging a job after another worker has reclaimed it.

The main branch (version 0.5.0) also sends webhooks, signed per the Standard Webhooks specification, with full-jitter retries that respect Retry-After, a dead-letter queue and replay. Every retry keeps the same webhook-id, so a receiver can drop repeats. The delivery guide runs it against a local receiver.

At-least-once work needs idempotent handlers. A durable inbox cannot make an external side effect happen exactly once.

Kill a sender mid-request +

Try it

From the same checkout, run the specification’s signing vector and the crash test. The crash test starts a real dispatcher process against a loopback receiver and kills it with SIGKILL during the request.

python3 -m unittest tests.test_standard_webhooks.StandardWebhooksTests.test_published_vector tests.test_dispatch.DispatchTests.test_crash_mid_delivery_redelivers_with_the_same_webhook_id -v

Expected: two passing tests. The signature equals the specification’s published vector. After the kill the delivery stays leased with one attempt; once the lease expires, another dispatcher sends the same body with the same webhook-id and a later timestamp.

Read the code

Read dispatch.py with standard_webhooks.py. Each attempt signs id.timestamp.body with every active secret, and its result decides success, a full-jitter retry raised to any Retry-After, or the dead-letter queue. Redirects are never followed.

A receiver can still see a message twice, so it should drop a repeated webhook-id. There is no rate limit or circuit breaker, and signing secrets are stored unencrypted.

TraceBench

An offline evaluation toolkit for recorded model outputs. Exact-match, contains and JSON-subset checks score English and Mandarin fixtures, and a baseline comparison shows which cases regressed. Latency and token cost come from the recorded data and are reported separately from correctness. Nothing calls a model provider.

On a nondeterministic system some cases flip between runs even when nothing changed. Version 0.5.0 on the main branch adds an exact McNemar test on the cases that changed status, paired bootstrap intervals and the smallest change a suite can detect, and --gate chooses what fails a build. In a simulation where 10% of cases flip at random, the default any-regression gate failed 99.4% of unchanged suites. The McNemar gate failed 1.1% (method and simulation).

Tell noise from a regression +

Try it

From the same checkout, record the 100-case synthetic baseline, then gate a noisy and a regressed candidate with the exact McNemar test.

mkdir -p reports
python3 -m tracebench evaluate --cases fixtures/paired/cases.jsonl --outputs fixtures/paired/baseline.jsonl --pricing fixtures/pricing.json --report reports/paired-baseline.json
python3 -m tracebench evaluate --cases fixtures/paired/cases.jsonl --outputs fixtures/paired/noisy.jsonl --pricing fixtures/pricing.json --baseline reports/paired-baseline.json --gate mcnemar
python3 -m tracebench evaluate --cases fixtures/paired/cases.jsonl --outputs fixtures/paired/regressed.jsonl --pricing fixtures/pricing.json --baseline reports/paired-baseline.json --gate mcnemar

Expected: exit codes 1, 0 and 3. The baseline passes 80 of 100 cases. The noisy candidate swaps 5 passing and 5 failing cases, so McNemar p = 1 and the gate passes. The regressed candidate breaks 12 and fixes 1: the pass rate falls by 0.11 (95% interval -0.18 to -0.04) and McNemar p = 0.00341797.

Read the code

Read paired.py. The exact McNemar p-value is a binomial tail over the cases that changed status, and the bootstrap resamples case pairs with a fixed seed. Gate decisions use integers and fractions; the McNemar gate fails only when p is below alpha and regressions outnumber improvements.

Cases are assumed independent and the gates judge pass/fail only. This 100-case suite can detect pass-rate changes of about 0.09 at 80% power, so small drops need larger suites.

Impact Ledger

A nonprofit reporting workbench with a typed frontend, a Python API and a SQLite store. Filter program records, tell unique participants apart from attendance, and compare session spending with the budget.

Sessions and attendance have separate grains, so a busy event does not multiply its own expenses. Imports validate before committing, and accessible tables keep the numbers available alongside the charts.

Every write also appends to a hash-chained audit log in the same SQLite transaction, and triggers reject edits and deletions of the log. verify detects edited, deleted or reordered entries and table edits that bypass the log. Past reports are rebuilt from the verified log, and undo-import adds a compensating batch instead of deleting history. The log is tamper-evident, not tamper-proof, and actor labels are self-declared (design).

Tamper with the history +

Try it

From the same checkout, run the audit tests. They tamper with real SQLite files, including after dropping the protective triggers.

python3 -m unittest discover -s tests -p test_audit.py -v

Expected: 15 tests pass. verify catches an edited, deleted or reordered entry and a table edit that bypasses the log, and a fully rewritten chain is caught only against a head digest saved elsewhere.

Read the code

Read append_batch and verify in audit.py. Each entry stores the row before and after the write and the SHA-256 of the previous entry, so changing any entry breaks every later link, and verify also replays each transition against the current tables.

Anyone who can edit the database file can rewrite the whole chain consistently; only a head digest kept outside the ledger reveals that. On a 25,000-entry ledger, an as-of summary took 315 ms. The same summary from the current tables took 68 ms.

From one webhook to one report

This example installs the three released tools and connects them through local HTTP services. The records are synthetic, with fictional English/Mandarin names such as Alex Chen / 陈安; the ledger itself stores only participant IDs.

  1. RelayBox accepts a signed event, deduplicates an identical replay and rejects a changed one.
  2. Its worker writes a receipt for each event, and a small adapter pulls the sessions and attendance CSV files out of those receipts.
  3. Impact Ledger previews the import without changing rows or reserving IDs. A separate import revalidates and commits atomically.
  4. The selected program and inclusive dates fix the population. Costs count each session once, and people count distinct IDs.
  5. TraceBench checks nine recorded JSON contracts, with no provider calls.

The receipt write, the CSV import and the inbox acknowledgment are separate transactions, so the chain as a whole is not exactly-once.

Make one cent fail

The clean run passes 9/9, exit 0. Changing the recorded actual spend by one cent, 13025 → 13024, gives 8/9, exit 3, and only import-totals regresses. Invalid input gives exit 2. This checks the recorded contract, not model quality.

Run it yourself

You need Python 3.11+. First download the three locked wheels as the README describes. Then, from the portfolio repository root, set WHEEL_DIR and OUTPUT_DIR to local paths outside the checkout whose parent folders exist and are trusted; the output folder must not exist yet. The command installs the wheels offline in a fresh environment.

python3 -B scripts/verify_handoff.py --wheel-dir "$WHEEL_DIR" --output "$OUTPUT_DIR"
