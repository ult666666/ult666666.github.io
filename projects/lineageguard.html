The problem

A data-change review has to coordinate more than a risk score: which source was read, whether its evidence is complete, which tasks finished, and what remains trustworthy after interruption.

I expanded the original LineageGuard demo into a source-bound workflow system. The visible graph represents compiled execution dependencies, rather than a predefined narrative attached to a final result.

The orchestration system

The typed composer rejects unknown capabilities, cycles, missing dependencies and invalid budgets before a read begins. A shared browser/Node interpreter runs independent evidence reads concurrently, tracks attempts and deadlines, and checkpoints actual state transitions.

Compatibility risk and evidence readiness remain separate. Unknown usage is not zero, truncated lineage is not complete, and BIGINT to SMALLINT is not treated as safe simply because both types are numeric. Deterministic policy—not an LLM confidence score—determines the review outcome.

Failure and recovery evidence

The local SQLite coordinator uses revision compare-and-swap, expiring writer leases and admission reservations. Tests interrupt a test-owned process after a committed checkpoint, reopen the database, refuse an obsolete writer and resume the same run identity in a new generation.

Complete, current outputs are reused only under an unchanged source and request binding. Changed input invalidates previous results and local acknowledgements. The browser exposes pause, reload, resume, cancellation, source-outage recovery, exact exports and comparisons between alternative plans.

The saved-comparison revision 5d7df02 verified on 26 October 2026 has 135 Node tests, 41 browser journeys across both storage modes and 19 evaluation assertions. These are separate, overlapping checks, not independent evidence of catalog truth. The original v2.0.0 release keeps its historical verification record; later launcher and Inspector changes are identified by their own commits.

Verify the exported review

Review Inspector checks the current review or an exported JSON file without uploading it, writing run history, opening a catalog connection or resuming a workflow. A recipient can inspect a review after it leaves the application instead of trusting a screenshot or a claimed checksum.

I reproduced an export inconsistency that survived a recomputed outer checksum: the final SQL draft no longer matched the completed step output. The added semantic guard checks result-to-step agreement, validates the embedded evidence, reproduces deterministic compatibility and policy, and regenerates the draft. The same guard now runs before JSON, Markdown and SQL exports.

The panel separates the recorded decision from the assessment of embedded evidence at inspection time. A previously valid review may now need fresh evidence. It shows source authentication as false: internal consistency is not authentication, a digital signature, independently observed execution or permission to migrate. The Inspector shares the same policy functions with the runtime; it is a replay check, not an independent policy implementation.

A local file remains local. The file-only CLI and browser panel reject malformed or ambiguous JSON and oversized inputs, clear stale success after refusal, and do not restore imported packages as runnable state. Browser tests disable networking during inspection and check that no request or checkpoint write occurs.

Compare two saved reviews

Open the Compare tab and choose two completed exported reviews. Both files pass the same semantic inspection before any difference appears. The report distinguishes recorded decisions from current evidence freshness and identifies alternative requests explicitly. No current run is needed.

The browser and file-only command share one comparison implementation and report schema. Selecting another file or clearing the panel invalidates an unfinished read and removes stale success. The comparison neither uploads files nor imports them into run history; existing run state remains unchanged.

Try the synthetic standard and strict reviews from the comparison guide, then download the report. Its zero new tool calls and false authorization flags remain visible. An internally consistent export does not authenticate its source or authorize a migration.

Try a three-minute engineering review

Compose and run. Open Studio, choose Revenue field rename, and run the review. Inspect a completed node: the graph, outputs and event trace describe actual execution. The decision remains a review result, not permission to execute SQL.

Break and recover. Choose Evidence-source outage and run it. The lineage step must fail rather than produce a favorable result. Select Restore synthetic source, then Resume run. Inspect the same run identity in a new generation and the completed evidence reused under its unchanged binding.

Carry and challenge the result. Open Review package and select Inspect current review. Export the verified run JSON, then select that file in Review Inspector. Compare the recorded conclusion with current freshness. A modified draft without consistent evidence must be refused. Finally, execute the evaluation suite and inspect expected-versus-observed outcomes.

My role, runtime modes and limits

I set the product scope, budget and safety boundaries and used AI-assisted implementation and regression design to build the compiler, runtime, evidence policy and review experience. The components are labeled honestly: deterministic stages are not presented as an autonomous LLM team.

The public browser-session preview executes against same-origin synthetic tools and stores checkpoints in the current browser. The local Node service adds durable SQLite state. Neither is advertised as an authenticated multi-tenant or distributed execution platform.

No SQL execution, catalog mutation or paid inference is enabled. A local review note is not organizational authorization. The optional DataHub capture is read-only and conservatively profiled; the release does not claim real-tenant validation.
