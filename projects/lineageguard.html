Case study: developer tools

LineageGuard Studio

A workbench for reviewing a database schema change against the lineage it affects. Each check runs as a step in a small workflow, every verdict keeps the evidence behind it, and a run that crashes resumes where it stopped.

The problem

Renaming a column looks harmless in one file. A revenue table, the dashboard built on it and a month-end job may all read that column. A useful review has to say which sources it read, whether that evidence was complete, and what still holds after a crash.

I rebuilt my earlier LineageGuard demo around those questions. The graph on screen is the program that runs, and every result stays bound to the source it was read from.

How a review runs

A typed composer rejects unknown capabilities, cycles, missing dependencies and invalid budgets before anything is read. One interpreter, shared by the browser and Node, runs independent evidence reads in parallel with attempt limits and deadlines, and checkpoints each state change.

Compatibility risk and evidence readiness are judged separately. Unknown usage is not zero, truncated lineage is not complete, and BIGINT to SMALLINT is not safe just because both types are numeric. The outcome comes from deterministic rules, and no language model runs in a review.

Measuring the policy

I wrote the labelling rules and the labels before the first benchmark run. That run found five decisions more permissive than their labels. One cleared a new ORDER_ID column next to an existing order_id, because names were compared with exact case.

After the fixes no decision is more permissive than its label, and CI fails if one becomes so. The benchmark now has 105 labelled cases, and 101 decisions match. The other four are stricter than their labels: lossless conversions that the policy does not try to prove safe.

Reading a dbt project

Most data teams keep lineage in dbt, so Studio can read a manifest.json, plus the catalog.json from dbt docs generate, as an offline evidence source. The same interpreter and policy then review the change.

Renaming fct_mrr.mrr_usd in a trimmed manifest from saas-analytics-warehouse, my synthetic dbt project, lists five downstream models and two exposures with their owners. It also finds the 12 dbt tests that read the model. The decision is needs-evidence: a manifest records what a project declares, not what the warehouse observes.

A manifest has no column lineage, query history or nullability, so evidence from it can block a change or ask for more, but never clear one. Studio reads manifest schema v12 and catalog v1 only, and refuses a manifest whose parent_map, child_map and depends_on disagree or whose graph has a cycle. A seeded property test compares the adapter’s lineage with an independent walk of depends_on.

Crashes and recovery

The local SQLite coordinator uses revision compare-and-swap and expiring writer leases. A test kills the review process after a committed checkpoint, reopens the database, refuses the stale writer and resumes the same run in a new generation.

Finished outputs are reused only while the source and the request are unchanged. A changed input invalidates earlier results and review notes.

The tests found two more bugs, both fixed: a type parser that let part of a blocked SQL statement escape its comment, and a summary that could add a fake decision line to the review brief. Catalog text that looks like instructions is treated as data.

Checking an exported review

Review Inspector checks the current review, or an exported JSON file, without uploading it, writing run history or calling a catalog. Whoever receives a review can check it instead of trusting a screenshot.

I found an export bug that a recomputed checksum missed: the final SQL draft no longer matched the step that produced it. The Inspector now checks each result against its step, replays the policy and regenerates the draft, and the same check runs before every JSON, Markdown and SQL export.

The recorded decision stays separate from how fresh the evidence is at inspection time. A pass means the file is internally consistent, which is not authentication or approval. The Inspector uses the same policy functions as the runtime, so it is a replay check, not an independent implementation.

Comparing two saved reviews

The Compare tab takes two exported reviews. Both must pass the Inspector before any difference appears, and the report keeps recorded decisions apart from current evidence freshness.

The browser and the command line share one comparison module. Nothing is uploaded or imported into run history, and choosing another file cancels an unfinished read.

Try it

  1. Open Studio, choose Revenue field rename and run the review. Select a finished step to see its output and the event trace.
  2. Choose Evidence-source outage and run it. The lineage step fails instead of returning a favorable result. Select Restore synthetic source, then Resume run: the same run continues in a new generation and reuses the evidence it already had.
  3. Open Review package, select Inspect current review and export the run. Load the file in Review Inspector and compare the recorded decision with the current freshness. If you edit the SQL draft in the file, the Inspector refuses it.
  4. Run the evaluation suite and compare the expected and observed outcomes.

Limits

  • The hosted demo is a browser-session preview against synthetic tools, with checkpoints kept in your browser. The local Node service adds SQLite. Neither is a multi-user or distributed system.
  • No SQL execution, catalog changes or paid model calls are possible, and a review note is not an approval.
  • The optional DataHub capture is read-only and has not been validated against a live DataHub instance.

I set the scope and the safety rules, and built Studio with AI coding assistants.
