Case study: fintech infrastructure

crossbook

An order-matching engine in Rust with opening and closing call auctions, crash recovery and a market-data feed. The same commands produce the same events on Linux, macOS, Windows, in the browser and on any number of threads.

The problem

A matching engine fails quietly. A wrong queue order or an off-by-one quantity still produces trades that look plausible, and nothing crashes.

So I wrote every rule down, made each command produce a fixed list of events, and had a second implementation check the first after every command.

The engine

Orders trade by price-time priority: the best price first, then the oldest order at that price. The engine supports limit and market orders, immediate-or-cancel, fill-or-kill, post-only, cancel, modify and four self-trade prevention modes.

Each side of the book keeps its price levels in a BTreeMap, and each level is a first-in, first-out queue threaded through one slab of 48-byte order nodes. A cancel is constant-time after the ID lookup. A dense price ladder would make level lookups constant-time too, but it needs a bounded price band.

The engine never reads a clock or a random number generator and never iterates a hash map, so replaying the same commands gives the same events everywhere.

How it is checked

A second, naive engine implements the same rules with linear scans. Property tests feed random command streams to both and require the same events and the same book after every command, along with structural invariants and conserved quantities.

CI pins the fingerprint of a 100,000-command session on Linux, macOS and Windows, and checks that the WebAssembly build replays one million commands to the same digest.

Mutation testing with cargo-mutants found untested behavior in the engine, the recovery code and the auctions. Each gap now has an assertion, and the testing notes explain the mutants that survive.

Recovery, market data and sharding

Crash recovery follows the write-ahead rule: a command is journaled before the engine applies it, and a checksummed snapshot records how much of the journal it covers. Recovery loads the newest snapshot and replays the rest, ignoring a half-written last command. A property test cuts the journal at a random byte and requires the uninterrupted run’s book and events.

The market-data feed builds trades and price-level updates from events alone. Subscribers use sequence numbers and heartbeats to notice a lost message and resynchronize from a snapshot.

A sequencer, worker shards and an ordered merge spread instruments across threads, and random streams must give the single-thread output for any shard count. On a four-core machine, sharding ran 2.6 to 3.4 times faster than one thread.

Call auctions

Version 0.3 adds the call auctions that exchanges use to open and close the day. During a call, limit and market orders rest without matching. Immediate-or-cancel, fill-or-kill and post-only orders are rejected, because nothing can execute yet.

The uncross picks one clearing price by the rules Xetra and Euronext publish: the most executable volume, then the smallest surplus, then market pressure, then the price closest to the reference, then the lowest price. Every crossing order fills at that price in price-time priority, market orders first.

A brute-force uncross that tries every price agrees with the engine on 20,000 random books, including ties at each rule. After every uncross, allocation invariants must hold, among them one price, no fill beyond a limit and an uncrossed book.

The engine finds the price in one pass over cached level totals, so the indicative uncross is cheap enough to refresh after every command: about 0.34 µs on a closing book of 8,452 orders. Journal and snapshot files moved to format version 2 and still read version 1.

Results

On one core of a 2.1 GHz Xeon cloud VM, the engine processes 15 to 16 million commands per second. Median latency is 64 ns per command.

Compiled to WebAssembly, the same session runs about half as fast under Node.js and produces the same event digest and state hash. These figures cover the matching core only, with no network, parsing or persistence on the timed path.

Limits

  • Books live in memory in one process, journals are written without fsync, and there is no network gateway or connection to a market.
  • The clearing price is always one of the orders’ limits, while Xetra uses the reference price when it falls between two candidates. There are no volatility interruptions, and the feed does not publish the indicative price.
  • The fast integer hasher is not resistant to hostile order IDs, so a gateway facing untrusted clients would assign IDs itself.
  • The exchange rules are summarized from public documents and cited without section numbers.
