quantkit

A Python library for option pricing (Black–Scholes–Merton, Cox–Ross–Rubinstein trees and Monte Carlo), mean–variance and risk-parity portfolios, a vectorized daily backtester and Value at Risk (VaR) model validation.

A strategy decides with prices through day t, and those weights earn day t+1’s return. A checker changes later prices and fails any strategy whose earlier weights move.

The VaR module forecasts one-day 99% VaR and expected shortfall with four methods, then backtests the forecasts with Kupiec’s and Christoffersen’s tests, the Basel traffic light and the Acerbi–Székely Z2 test. Those tests make mistakes too: over a year of trading days, a correct model fails Kupiec’s 5% test almost one time in ten. On fat-tailed returns, Z2 rejects a Gaussian model almost twice as often as the exception count does.

The walk-forward guide sets monthly allocations from earlier closes only and compares strategies on the same dates and costs, with timing tests for each step.

Reject a VaR model with thin tails +

Try it

From the same checkout, run the size and power simulations of the VaR backtests.

uv run pytest tests/test_var_size_power.py -v

Expected: 3 passed. Forecasts scored on returns drawn from their own model fail each test at the rate the exact calculation predicts, and Gaussian VaR on Student-t(4) returns is rejected far more often, by Z2 more often than by the exception count.

Read the code

See null_rejection_rates in backtests.py. A dynamic program over the days tracks the first and last day’s state, the number of exceptions and the number of consecutive pairs. Those four numbers fix every test statistic, so each test’s true size is computed, not assumed.

Even a correct 99% model sometimes goes a whole year without an exception (8.1% of the time), and that alone fails Kupiec’s test. The p-values stay asymptotic; the exact sizes show how far off they are.

powerlift

Experiment design and analysis in Python: sample sizes and power, frequentist and Bayesian comparisons, multi-arm (A/B/n) tests, CUPED variance reduction, sample-ratio-mismatch checks and multiple-testing corrections.

Group sequential boundaries come from the joint normal distribution of the interim z-statistics, so a team can look early without inflating its false-positive rate. Looking early without them is costly: in the README’s simulation, stopping A/A tests at the first significant look out of ten flags 19.5% of them. The target is 5%.

For A/B/n tests, Dunnett’s test compares every variant with one control and keeps the chance of any false win at 5%. In simulated experiments with six variants and no real effect, unadjusted tests found a false win 20.4% of the time. Dunnett’s test found one 5.4% of the time.

The experiment walkthrough reads a seeded per-user CSV, checks allocation and the outcome window, and ends with a CUPED readout, including a result that stays inconclusive. The A/B/n walkthrough covers multi-arm sample sizes and readouts.

Hold the false-win rate across variants +

Try it

From the same checkout, run the SciPy comparison and the family-wise error simulation.

uv run pytest tests/test_many_to_one.py -k "scipy_dunnett or family_wise" -v

Expected: 2 passed, 32 deselected. Statistics and adjusted p-values agree with scipy.stats.dunnett on generated datasets, and experiments with no real effect produce a false win at the rate each adjustment predicts.

Read the code

See max_t_cdf in _dunnett.py. Every treatment-versus-control statistic shares the control mean, so their correlations have a product form. Given the control’s noise and the pooled variance they are independent, which turns a k-dimensional integral into a two-dimensional one that the trapezoidal rule evaluates deterministically.

The comparisons are many-to-one and single-step, and they pool the variance of all arms. With very unequal variances, pairwise Welch tests with an adjustment fit better.

ledgerline

A double-entry ledger API built with FastAPI and SQLAlchemy. Journal entries are integer minor units that must balance per currency, posted transactions are immutable, and corrections are reversals.

Each write is one database transaction that replays the stored response for a repeated Idempotency-Key and compare-and-swaps every account version it touches, so concurrent requests cannot overdraw an account.

Holds work like card authorizations: reserve an amount now, then capture all or part of it, void it or let it expire. Each account reports its ledger, held and available balances. Holds and postings draw on the same available balance, so held money cannot be spent twice, even under concurrent requests.

The API walkthrough runs each hold step over HTTP, and the design notes explain the state machine. The wallet demo runs a disposable wallet over local HTTP: a retried request, a rejected overdraft, a reversal and a reconciliation.

Try it

From the same checkout, run the hold concurrency tests.

uv run pytest tests/test_holds_concurrency.py -v

Expected: 8 passed. Forty concurrent holds race for a balance that fits 33 of them, and 33 succeed. Holds and transfers racing on one account share one available balance, and ten racing captures and voids of one hold produce one winner. CI repeats the suite on PostgreSQL 17.

Read the code

See create_hold and capture_hold in service.py. The test races 30-cent holds against a 1,000-cent balance. A hold changes no balance, but it bumps the source account’s version, so concurrent holds and postings serialize through the same compare-and-swap. Each hold allows one capture, and expiry is computed when a hold is read, so nothing fires when a hold lapses.

saas-analytics-warehouse

Analytics engineering for a fictional SaaS company. A seeded generator writes eight raw tables, a dbt and DuckDB warehouse models MRR movements, cohort retention and unit economics, and a report rebuilds its charts.

Every customer-month’s MRR change gets exactly one label (new, expansion, contraction, churn or reactivation), so the monthly bridge has to reconcile to the cent.

Six staging models load incrementally. Each run reprocesses the last seven days and replaces rows by key, so a row up to a week late is absorbed and a newer invoice version replaces the old one. A dbt snapshot keeps each customer’s plan, seats, price, MRR and status as type 2 history.

A load simulation lands the data day by day, with some rows arriving late, and compares 24 relations with a full refresh by row hash. At this size incremental runs are not faster, because the sources are CSV files read in full; the design notes explain the trade-offs.

The churn investigation traces one month from the MRR bridge to the customers behind it, reconciling cents and customer counts before it writes any report.

searchlite

A zero-dependency TypeScript search engine: Porter stemming, a positional inverted index, BM25F ranking across weighted fields, a query language with phrases, prefixes and fuzzy terms, highlighting, and hybrid retrieval with reciprocal rank fusion.

explain() rebuilds a result’s score clause by clause and field by field, and a test requires it to equal the score the search returned.

Postings are stored as compressed blocks of 128 documents, each with a skip entry and a score bound. Queries run document at a time with MaxScore and block-max bounds, and property tests require the same documents, order and scores as scoring every match. On 10,000 synthetic documents, pruning made median top-10 queries 7 to 15 times faster on one machine, with identical rankings (how it was measured). Gains are smaller at 1,000 documents, one phrase-heavy query is slower, and block-max WAND is not implemented.

The relevance workbench compares two ranking setups query by query, with judged grades and missed relevant results. Its report matches the command-line one, with scores agreeing to about twelve decimal places. The local-file workbench does the same for your own saved indexes and judgments, in a browser worker, with files kept in the page’s memory (workflow and limits).

The local docs walkthrough indexes a folder of documents, saves a snapshot and answers queries from it with snippets and score explanations. You can label your own questions and fail a check when a query drops below its threshold.

Skip work without changing a ranking +

Try it

From the same checkout, run the pruning property tests.

npx vitest run test/engine/pruning.test.ts

Expected: 19 passed. On random corpora, queries, filters and result limits, pruned top-k results equal exhaustive scoring, and a version 1 snapshot from searchlite 0.2.0 loads with identical results.

Read the code

See daat.ts. A top-level OR runs MaxScore in windows that end at a block boundary, so each clause’s block bound holds for the whole window. Clauses whose summed bounds cannot beat the current k-th score supply no candidates, and a window where no clause can compete is skipped without decoding it. Bounds carry a small safety margin, so a document is dropped only when it cannot enter the top k.

Pruning skips scoring, not statistics: IDF still counts every match, and phrases are matched in full.

contrastkit

WCAG 2.2 contrast checks, OKLCH fixes for failing pairs, color-vision-deficiency simulation and palette audits: a zero-dependency TypeScript library, a CLI that can gate design tokens in CI, and a React app.

A fix keeps the hue and changes only OKLCH lightness, searching both directions for the closest passing color. Ratios are truncated, so a near miss never displays as a pass.

Besides the three dichromacies (a missing cone type), the simulation covers the more common milder forms, protanomaly, deuteranomaly and tritanomaly, at any severity from 0 to 1. It interpolates between the matrices Machado, Oliveira and Fernandes published in 2009, and severity 1 reproduces the dichromacy. Audits, the CLI’s --cvd option and a keyboard-operable slider in the Palette Auditor all take a severity.

The web-to-CLI walkthrough downloads a palette as tokens JSON, audits it with the CLI, applies the suggested fix and audits again.

citecheck

Question answering over a document collection with the Claude API. Passages come from a SQLite FTS5 index ranked with BM25, the model must cite a retrieved passage for every sentence through a strict tool schema, and the app abstains without a model call when nothing relevant is found.

A checker rejects citations to passages that were never retrieved, splits each sentence into claims and compares every claim with the cited clause it restates. A flipped negation, “must” where the source says “may”, a word swapped for its opposite, or a number or unit that differs makes the claim unsupported.

On held-out labelled claims, the claim-level checker caught 44 of 48 unsupported sentences; the earlier word-overlap checker caught 20. It wrongly flagged two supported sentences where the old checker flagged one. One author wrote both the cases and the rules, so these figures are optimistic, and the design notes list every remaining miss.

Tests and the bundled evaluation replay hand-written synthetic responses, so no API key is needed and no real model output is claimed. Live mode uses your own key. Index tests check that a heading inside a fenced code block does not start a new citation section.
